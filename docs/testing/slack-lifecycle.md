# Slack delivery verification

Slack tool progress is optional per routed Slack channel entry and is off by default. A run displays at most one temporary progress message. It waits one second before creating that message, edits at most every two seconds, and shows up to eight registered tool invocations. Progress text contains only the registered tool name and a generic state. Private tool turns emit no public tool progress.

Before terminal delivery, the presenter stops progress scheduling and queued 429 waits, then waits for a dispatched write to finish or reach its five-second deadline. Slack `show_typing` follows the selected agent/channel route, including routes sharing one connection. Native assistant status uses fixed `is thinking` text and refreshes every 60 seconds. It stops before the terminal write. A confirmed new reply or file share lets Slack clear native status; intentional silence and edit-only outcomes clear it explicitly. Status calls have a five-second limit and start only within the shared shutdown deadline; a call already dispatched may finish under its own limit. Slack may not support native status on every conversation surface, in which case the run stops trying that surface. Native activity remains best effort; reliable channel-thread and concurrent-run activity are tracked separately in #30.

An answer is confirmed only after every text part or the completed Markdown file share succeeds. The file workflow allocates an upload URL, uploads bytes, then completes the share. Plain-text fallback is safe before completion is attempted. A failed completion permits fallback only when Slack definitely rejected it. Transport failures, server failures, and unknown Slack API errors have uncertain acceptance, so the answer is not resent. Already accepted text parts stay in the thread, followed by a fixed incomplete or unconfirmed-delivery notice when Slack permits it. `NO_REPLY` remains silent.

The Web API delivery helper retries only explicit 429 responses with a valid `Retry-After` delay that fits its remaining deadline, up to three retries. It does not retry connection or 5xx errors. Answer delivery has a 45-second budget, fixed failure notices get a fresh 15-second budget, and progress cleanup gets a fresh five-second budget. Each operation starts with the remaining shared shutdown deadline when draining; no new write starts after that deadline. The temporary progress message is deleted after a confirmed answer or accepted standalone outcome. A failed cleanup remains visible and is reported operationally.

Every admitted Slack run records only its original installation, workspace, configured route, channel, root thread, and delivery state before tool or model execution. Progress creation records its timestamp and cleanup ownership. Confirmed terminal delivery is recorded before progress deletion. The presenter holds the terminal callback through shutdown draining: a completed answer or intentional silence stays final even if shutdown begins during its delivery, while interruption before completion uses a fixed notice. A runner stop says `Interrupted; please resend your request.` and a user stop says `Stopped.`. Checkpoints contain no prompt, media, answer, tool fields, or credentials.

Recovery starts only after Slack authentication and route publication, before slow identity-cache refresh. It matches the original agent, configured route, installation, and workspace; sends only to the recorded channel and root thread; and never reconstructs or resends an answer. A handled checkpoint only deletes known temporary progress. Pending work edits a known progress message to a fixed notice; a standalone notice is attempted only after an uncertainty marker is saved. A crash after that marker, an unknown transport result, or an unknown delivery state retains the checkpoint without a new post. A definite rejection clears the notice marker for a later bounded retry while preserving any uncertainty about the earlier answer. Missing routes, rejected permissions, corrupt records, and denied cleanup retain their checkpoints for operational repair. Old targetless Slack records are retired without replay. Startup, reconnect, and explicit recovery perform bounded passes; there is no background retry loop.

If Slack accepts an answer just before the process exits, but the acceptance checkpoint write has not completed, recovery may add one fixed notice to the same thread. It does not resend the answer. A long restart, missing route, or permanent stop can leave work undelivered; bounded retries are not a delivery guarantee.

For private delivery, local assistant history is appended once only after every answer part or file share is confirmed. A crash between Slack acceptance and that local append can leave the history entry absent. Recovery has no answer body and does not fill this gap or duplicate a reply.

Run `pnpm test:go`, `pnpm test:e2e`, and `pnpm lint` after code changes. The channel tests use a fake Slack HTTP server for 429 and staged-upload failure cases. The presenter tests cover progress timing, silence, multipart delivery, partial delivery, uncertainty, and cleanup. For an authorized test installation, set `AVIARY_SLACK_SMOKE_FILE` to a protected JSON file containing `bot_token` and `channel`, then run `go test ./internal/server -run '^TestSlackPresenterLiveSmoke$' -count=1 -v`. This leaves a clearly labeled synthetic progress state visible for eight seconds after its edit, then posts a synthetic final answer and removes temporary progress. The root and final answer remain for inspection. Never place that fixture in the repository or print its token.

A runner terminal event can arrive before deferred usage or checkpoint teardown finishes. Tests that change the global store root must call `AgentRunner.Wait()` after receiving a terminal event and before resetting the root; otherwise the race detector can report a store-root read/write race. The focused regression command is `go test -race ./internal/agent -run 'TestAgentRunner_ErrorCases|TestNoProviderDoesNotExposeModelToSlackDelivery|TestPreparationErrorDoesNotReachRegisteredSlackDelivery' -count=1`.

On 2026-09-27, the opt-in presenter smoke passed in the `bvt-test` installation: it created a synthetic progress message, posted the final answer, deleted progress, and read back the thread. This verified outgoing presenter and transport behavior. It did not exercise Socket Mode routing, a live runner turn, or native assistant status.
